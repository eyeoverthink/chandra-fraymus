# Chandra-FRAYMUS

Autonomous AI agent workspace with intelligence stack — Express server (port 8787) + Vite React frontend (port 5173).

## Quick Start

```bash
npm run dev          # concurrently runs server + client
npm run server       # Express only (needs .env)
npm run client       # Vite only
npm run build        # production client build
npm run start        # production server (serves built client)
```

## Architecture

- **Server:** Node.js ESM, Express 4, better-sqlite3 (WAL mode), WebSocket broadcast
- **Client:** Vite + React, 4-view Nexus interface (Command Center, Constellation, Canvas, Library) + Detail Drawer for 13 panels, useWebSocket hook for live updates
- **LLM:** Ollama at localhost:11434 (configurable via OLLAMA_BASE_URL)
- **DB:** SQLite at `data/chandra.db`, migrations in `server/db-migrate.js`
- **Auth:** Bearer tokens via `server/mcp/auth.js`, loopback-only binding

### Memory search — agents recall by meaning, and the gain is a number (server/intelligence/memory-*.js) — 2026-11-11
- **Why:** the first mechanism absorbed from gbrain (see the ranked list under the flat look). `recallMemories` was `key LIKE '%query%' OR value LIKE '%query%'`: a question in a sentence matched nothing. And `buildPromptContext(agentId, taskText)` **ignored its second argument** — every agent prompt carried its ten newest memories whatever the task was (the caller did not even pass the task).
- **`memory-rank.js` (pure):** `ftsQuery` (every word quoted, so nothing typed is query syntax; all words, then any word), `rrfFuse` (k = 60), `fuse` = 0.7 · normalised RRF + 0.3 · cosine with near-duplicates dropped (word-set Jaccard > 0.85), and the measures: `precisionAt`, `recallAt`, `reciprocalRank`, `ndcgAt`, `hitAt`, `summarise`, and a seeded paired sign-flip test `signFlipP`.
- **`memory-bench.js` (pure):** `generateBench({seed})` — 300 memories and 120 questions generated together, so the gold answers cannot drift from the corpus. Four kinds, one per way a search fails: `exact` (a phrase of the memory), `natural` (the same words in a sentence), `inflected` (other word forms), `paraphrase` (other words for the same things; shares no content word with its memory). One best memory (grade 3), partial ones (grade 1). `conceptEmbedder()` is a test embedder that knows the generator's synonyms.
- **`memory-search.js`:** `createMemorySearch({db, embed})` — a factory, so the benchmark runs the same code on a generated corpus in a throwaway in-memory database. Keyword arm: FTS5 `agent_memories_fts` (external-content table over `agent_memories`, `tokenize='porter unicode61'`, kept current by three triggers, rebuilt once on first run), ranked by `bm25`. Vector arm: `agent_memory_vectors` (memory_id, model, dim, Float32 blob, content hash) from the local `nomic-embed-text` with its `search_document:` / `search_query:` prefixes, cosine in memory (cached per agent). **The vector arm is optional at every step** — no model, a dropped scheduler slot or a memory not yet embedded all fall back to keyword search, and the result says which arms answered. Every candidate gets a cosine (its own, or the candidates' median when it has no vector yet): with a tenth of the store embedded, vector-only rows were out-scoring better keyword matches. Nothing in `agent_memories` is rewritten; both indexes can be dropped and rebuilt.
- **`memory-search-service.js`:** the live instance; `searchMemories(agentId, query, opts)` (async, never throws) and `relevantMemories(agentId, text)` (synchronous, keyword only — a prompt never waits on a model). Indexer: a batch of `MEMORY_INDEX_BATCH` (128) every `MEMORY_INDEX_INTERVAL_MS` (60 s) at the `background` class (queries embed at `agent_run`); started and stopped with the daemon; `MEMORY_VECTORS=0` turns vectors off. `getDaemonStatus().memorySearch`. Routes: `GET /api/intelligence/memory-search`, `GET …/query?q=&agent=&mode=hybrid|keyword|vector|like&limit=`, `POST …/index`, `POST …/bench {seed}`, `GET …/bench`. Table `memory_bench_runs`; each run reports `lost` — questions the previous run of that seed answered first and this one did not (**the regression gate**).
- **Consumers:** `buildPromptContext` now puts up to six memories that are *about the task* ahead of the newest (and `fleet/runtime.js` passes the last user message, which it never did); the `agent_recall` tool searches by meaning and returns `score` and `matchedBy`. `recallMemories` itself is unchanged for its other callers.

### Facts — what is true now (server/intelligence/facts.js + facts-service.js) — 2026-11-11
- **Why:** the second mechanism from gbrain. `agent_memories` is a pile of notes: when a number changes, the old note and the new one sit side by side and a search returns both. A fact is one claim about one entity, and asserting it does exactly one of three things — **duplicate** (same fingerprint, or the same statement in other words: `seen_count` goes up and the claim is renewed), **supersede** (the same statement with a different number, date or a flipped negation: the old row gets `expired_at` and `superseded_by` and is **never deleted**), or **new**.
- **`facts.js` (pure + factory):** `normClaim`, `entitySlug`, `factFingerprint` (sha256 of entity + normalised claim), `claimParts` (subject words / value tokens / negations), `claimsDiverge` (do the value tokens or the presence of a negation differ), `claimLikeness` (word-set Jaccard with values left out; `SAME_STATEMENT` 0.6), `decayed` (confidence halves every `HALF_LIFE_DAYS`: event 7, commitment and preference 90, belief / fact / idea 365). `createFactStore({db, clock})` → `assertFact`, `currentFacts`, `history`, `entitiesIn(text)` (whole-word match, longest first), `expire`, `stats`. The rule is gbrain's finding turned into code: similarity alone cannot find an update (0 of 97 on their labelled set); an update is *the same sentence with a different value*.
- **Reading facts out of notes — a model proposes, code decides (`grounded`):** every proposed fact must **quote** the memory it came from; the quote must really be in it; the entity must be named in the quote; every number in the claim must appear in the quote. Anything else is dropped and counted by reason (`no_quote`, `quote_not_in_source`, `entity_not_in_quote`, `number_not_in_quote`). The reader takes `FACTS_READ_BATCH` (3) memories every `FACTS_READ_INTERVAL_MS` (10 min) at `background` priority from outcome / insight / world / hive / fossil / research / dossier memories, with a watermark in `facts_state`; a dropped model call stops the batch and the memory is tried again. `FACTS_READER=0` turns it off.
- **Consumers:** fleet tools `fact_assert` and `fact_lookup` (registered in `app.js`); a "Known facts" block in an agent's prompt when its task names an entity (`factsPromptContext`, synchronous, ≤ 5 facts, expired versions never shown); routes `GET /api/intelligence/facts[?entity=]`, `GET …/facts/history?entity=`, `POST …/facts {entity, claim, kind?, confidence?}`, `POST …/facts/read`, `POST …/facts/bench`, `POST …/facts/:id/expire`. `getDaemonStatus().facts`.
- **Measured (`runFactsBench`, three seeds):** 360 statements about 60 changing truths — a fact store answers the current value **1.00** of the time and shows a stale value **0 %**; the same notes kept as a pile (the newest five about a thing) answer 0.65–0.67 and show a stale value 15 %. Every past value is still readable in both. `test/facts.test.js` (6) holds these. **This is the easy half:** the generated statements are clean. Reading facts out of real notes with a 14B model is the hard half; its acceptance and drop counts are in the status, and nothing yet measures whether accepted facts are *right*.

## Code Conventions

- ESM throughout (`"type": "module"` in package.json)
- Shared commerce utilities in `server/commerce/shared.js` — always use `shopifyHeaders()`, `shopifyBase()`, `chatOllama()`
- All async Express routes wrapped in try/catch forwarding to `next()`
- All fetch calls use `AbortSignal.timeout(15_000)` for external APIs
- Query params: always coerce and clamp (e.g., `Math.min(500, Math.max(1, parseInt(val) || 100))`)
- WebSocket: server heartbeat (30s), client exponential backoff
- Error responses: always `{ error: 'message' }` JSON
- DB ownership: scope DELETE/UPDATE queries with `AND user_id = ?`
- Shopify API version: `2024-10` (centralized in shared.js)
- No silent `catch {}` blocks — always log `e.message`

## Operational Rules

### Skills Stay Live (Phase T)
The five `/chandra-*` skills in `.claude/commands/` and the README "Live Inventory" carry generated blocks between `<!-- skills-sync:begin NAME -->` / `<!-- skills-sync:end NAME -->` markers. **Never hand-edit inside a marker block.** After adding a panel, route, module, tool, node type, agent manifest or README phase section, run `npm run skills:sync`; `npm run skills:check` exits 1 when a block is stale. Generator: `scripts/skills-sync.mjs` (reads filesystem, `data/chandra.db`, `GET /api/health`). Blocks: `inventory`, `routes`, `intelligence-modules`, `fraymus-modules`, `tools`, `panels`, `node-types`, `phases`, `vitals`, `agents`.

### Push After Pause
After every ~1 hour pause in a session, push all work to git before stopping. When resuming after a pause, read `F:\claude-brain\context\brain-dump.md` instead of re-reading the full session context — this saves credits and preserves continuity.

### Continuity Folder
`F:\claude-brain\` is the cross-agent continuity folder:
- `memories/` — All Claude memory files exported verbatim (FULL-MEMORY-EXPORT.md)
- `sessions/` — Session transcript exports (zip files)
- `context/` — Brain dumps and context summaries for any agent to absorb

When starting a new session on this project, check `F:\claude-brain\context\brain-dump.md` first. It contains everything a new agent needs: who Niles is, what the system does, critical rules, architecture, and pending work — without re-reading paid conversation history.

### Session Export
At the end of significant sessions, export the transcript to `F:\claude-brain\sessions\` so other agents can reference past decisions without re-reading the full conversation.
