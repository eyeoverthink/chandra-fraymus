## Findings and closure criteria

### INT-21-01 — P1: all three neural integrations use a nonexistent method

`self-narrative.js:238`, `dream-solver.js:200` and `intelligence-monitor.js:216` call `ctrnn.injectGaussian(...)`. `ctrnn-instance.js` returns the object from `createCTRNN()`, whose public entry point is **`inject(x, y, sigma, amplitude)`** at `ctrnn.js:435`; `injectGaussian` is private to that factory.

Against the actual CTRNN object, all three operations return apparent results while the external input array remains entirely zero. A direct call to public `inject()` changes that same array, proving the core control works. Each consumer silently catches the nonexistent-method error.

There is a second contract error hidden behind the first: callers pass amplitude third and sigma fourth. Merely renaming the method would reverse width/strength. For example, the narrative's intended amplitude 0.6 / sigma 2.5 is passed as `(2,8,0.6,2.5)`. The public function also uses x/y coordinates; document and test whether a claimed row/column needs conversion.

Closure: use the actual public API and argument order in all three consumers, with explicit coordinate meaning. Assert the resulting input field's center, width and sign against the actual core, including monitor inhibition. Surface injection failure. A mock invented with `injectGaussian()` is insufficient acceptance evidence.

### INT-21-02 — P1: all three new fleet action modes silently return status

New tool executors at `fleet/tools.js:527`, `:546` and `:565` read bare `params.mode` / `params.problem`. The actual runtime calls **`tool.execute({ args }, ctx)`**. Thus `self_narrative_status(mode=generate)`, `dream_solver(problem=...)` and `intelligence_monitor_status(mode=assess)` all take the status branch.

The actual executor probe observes no additional model calls or assessment after requesting all three actions. A bare-parameter direct call successfully solves a fixture problem, explaining why direct tool-object tests can miss this. This repeats the lineage contract defect already reported and fixed earlier.

Closure: destructure `{ args }` consistently; verify all action and status modes through actual fleet dispatch. Add the executor-contract check to the feature creation/verification process so new tools inherit the correct convention.

### INT-21-03 — P1: narrative work overlaps and commits after Stop/reset

The 120-second async interval at `self-narrative.js:313` has no in-flight guard. Its cooldown is based on the last **completion** timestamp, so a sufficiently slow generation allows a second request while the first is pending. The shared Ollama helper permits requests up to 180 seconds, longer than this interval.

`stopNarrative()` only clears the timer; `resetNarrative()` clears fields without invalidating pending generations. The probe holds two interval requests unresolved, calls the same stop/reset functions used by `stopDaemon()`, then resolves them. Both publish `system.narrative` events and repopulate the reset narrative while `running` remains false. No elapsed-time sleeping or real model request is needed to reproduce it.

Closure: serialize or skip overlapping scheduled work, abort pending requests where supported, and use a lifecycle generation token before any state/DB/bus/neural commit. Test completion after stop, after reset, after restart and out of order. Preserve deliberately authorized on-demand operations as an explicit separate contract rather than conflating them with stopped scheduled work.

### INT-24-01 — P2: monitor freshness contradicts producer cadence and hides zero effectiveness

The monitor treats most log rows older than **120 seconds** as stale. Those rows are sampled snapshots, not per-tick heartbeats. For example, sensory writes every 60 ticks at 5 seconds (**300 seconds**), emotional feedback every 30 ticks at 10 seconds (**300 seconds**), resource envelope every 30 readings at 10 seconds (**300 seconds**), and metacognition every 30 assessments at 30 seconds (**900 seconds**).

Using actual producer schemas, the probe supplies fresh rows and observes 12 active subsystems. Advancing only 180 seconds causes the expected sensory/emotional/resource rows to be classified stale, before their next ordinary snapshots would be due. Normal monitoring can therefore generate false degradation/inhibitory intentions. This cadence inference does not establish the cause of every degraded live status.

There is also a masking error: `row.effectiveness || 0.5` maps known zero metacognitive effectiveness to score **0.5**, above the degradation threshold. Similar zero fallbacks appear in predictive/active-inference checks.

Closure: use live status/explicit liveness heartbeats or freshness bounds derived from each producer's persisted cadence and startup grace period. Preserve zero scores, bound values and distinguish idle/unknown/error from unhealthy measured behavior. Test several healthy snapshot periods before calibrating alerts. The current code emits recommendations and Gaussian intentions; it does not implement a deterministic circuit breaker or parameter auto-tuning.

### INT-21-04 — P2: narrative reads incorrect Heart and gate fields

`self-narrative.js:71` reads `gate.proven?.proofsPassed`, but `proven` is a boolean and the producer exposes `gate.proofsPassed` at the top level. It therefore reports zero proofs even in the four-proof contract fixture.

The same collector reads `mood.intensity` / `mood.sentiment`, while this commit's actual `Heart.recentMood()` returns `intensityAvg` / `sentimentAvg`. The actual Heart fixture has positive nonzero averages; the collected narrative context replaces both with zero. Mood name/distribution survive, but the supposed grounded narrative loses important source data.

Closure: align producer/consumer schemas and test with the actual Heart output and the gate's actual return shape. Verify prompt input values, not just that the model generated text. Keep unavailable data explicit instead of silently substituting a grounded-looking zero.

### INT-22-01 — P2: neutral text generates false compound emotions

Heart's existing no-lexicon fallback assigns 0.12 to every normalized emotion. The new `detectCompounds()` compares those pseudovalues to thresholds as low as 0.10/0.12. The actual `Heart.feel('table pencil notebook')` returns primary `neutral`, all raw emotion scores zero, yet compounds **awe, jealousy and hope**.

The explicit joy/sadness control correctly produces bittersweet, and the history retains the intended 50-frame maximum. However, `getMoodTrajectory(1)` produces nonfinite shift/stability because its second half is empty. History is also module-global/in-memory, not a distinct persisted history per Heart instance.

Closure: gate compound detection on real supported evidence/meaningful primary scores and calibrated confidence, handle neutral input, and validate trajectory window size. Add neutral/unrelated-text and explicit-blend controls. Define history ownership. The **12 compound definitions are explicitly hardcoded** in `COMPOUND_EMOTIONS`; the implemented feature recognizes listed combinations, not previously undefined emotion categories.

### INT-23-01 — P2: default dream-solver paths never supply the signing dependency

`solveDream(problem, { trigger, dreamer = null })` supports recording through `dreamer.dream`, but the normal REST handler (`dream-solver.js:320`) and fleet action both call it with only `trigger`. The daemon wires its CTRNN, not a Dreamer dependency, and does not run it as an automatic solve step.

The actual isolated REST solve returns `dreamNumber: null`. A direct call supplying a fixture Dreamer returns number 17, proving the conditional path exists. That is a dependency-wiring control, not a real Ed25519 signature test. Existing Dreamer source supports signed files when identity is supplied, but this new default path never reaches it.

Closure: inject the configured Dreamer through the supported normal path; expose recording/signature success and failures explicitly. Test a REST solve and fleet solve producing and verifying a signed artifact, and a signer failure without claiming a signed result. A solver ready status does not mean a solve or signature has happened.

### INT-21-05 — P2: model zero ratings and failures become positive-looking outcomes

Both narrative and dream solver use `parseFloat(value) || 0.5`. Legitimate model ratings of zero become **0.5** for all four scores (coherence, awareness, novelty, feasibility). These are model opinions rather than independently measured abilities, and the zero default further misrepresents them.

When the model throws, dream solver returns a solution-shaped fallback, novelty 0.2 / feasibility 0.1, stores a session and publishes the ordinary `system.dream-solve` event without an error/status field. Its text says the problem remains in a dream queue, but this path performs no queue operation. If neural wiring were repaired, those fallback scores would also drive creative-spark intentions.

Closure: validate the full model schema and preserve finite zeros; distinguish generated, failed and fallback outcomes. Keep model-reported scores labeled as such. Report error/retry status and create a real queue entry before claiming one exists. Do not treat a model failure as evidence of a creative solution.

### INT-23-02 — P2: failed storage still returns success and publishes an ordinary solve event

A trigger rejecting only `dream_solver_sessions` inserts leaves no stored session, yet `solveDream()` returns its normal ID/result and publishes `system.dream-solve`. The database error is silently discarded, and the response has no persistence status. This repeats the chart persistence failure pattern from the previous review.

The new narrative and monitor status fields named `snapshotsStored` also report invocation counts, although persistence occurs only every tenth call. In the probe both counters are nonzero while their tables contain zero rows. Their cached last states and counters are not restored from history on module initialization.

Closure: distinguish computation from durable recording, log/return storage failure, publish appropriately labeled events after successful storage or mark non-durable outcomes, and count stored rows accurately. Document sampled history and process-local status versus persisted state. Verify insertion rejection, retry and restart behavior with a disposable database.
